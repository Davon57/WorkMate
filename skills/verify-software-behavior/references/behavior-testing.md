# 面向行为的测试

## 判断测试价值

优先保护出错代价高、逻辑密度高、回归概率高或与真实缺陷直接相关的行为。避免为纯转发封装、第三方库行为或静态配置编写低价值测试。

## 选择测试层级

- 纯业务规则和数据转换：单元测试。
- 具备稳定组件测试设施的独立用户交互：组件测试。
- 项目自有子系统之间的边界：集成测试。
- 关键的跨页面或部署后用户路径：端到端测试。
- 视觉行为：使用项目已有的视觉回归工具，否则提供明确的人工验证证据。

选择能够观察真实契约且成本最低的测试层级。若仓库已有另一种成熟方案能够可靠保护行为，遵循项目惯例。

## 测试质量审查

始终询问：如果完全重写实现但公开行为保持不变，这个测试是否仍应通过？

发现以下情况时，拒绝或修改测试：

- 断言私有状态、ref、辅助函数名称或偶然的方法调用；
- 在测试中重复生产代码的实现分支；
- 大量模拟项目自有代码，导致真实集成错误无法暴露；
- 只执行代码而没有有效断言；
- 依赖固定等待、不稳定选择器、偶然顺序或无关数据；
- 为通过测试而降低断言、添加跳过或吞掉错误。

优先采用描述行为的测试名称、真实输入、公开输出、可访问性查询、确定性夹具以及仅针对系统边界的模拟。

# 验证软件行为

把测试作为持久的行为契约，不要把测试写成实现的复述或覆盖率填充物。

## 工作流程

1. 将需求、验收条件、缺陷证据和变更目标转换为用户可观察的 Given/When/Then 行为契约，并标明假设。
2. 提出测试方案前，先发现代码仓库真实存在的验证能力。完整阅读 [references/capability-discovery.md](references/capability-discovery.md)。
3. 为每个有价值的行为选择成本最低、能够可靠保护行为的既有测试层级。编写或评审测试前，完整阅读 [references/behavior-testing.md](references/behavior-testing.md)。
4. 对可稳定复现的缺陷，优先在修改生产代码前编写能够复现问题的失败测试。若修复已经完成，明确说明没有观察到修改前失败。
5. 遵循相邻代码已有的框架配置、测试风格、辅助函数、夹具和执行命令。不得编造账号、接口、数据、选择器、服务或命令。
6. 先运行最小相关测试，再运行与风险相称的静态检查和相关回归测试。不得为了得到绿色结果而弱化断言、跳过测试或替换失败命令。
7. 将失败归类为产品代码、测试代码、环境、既有失败或未知。保留证据；若继续处理需要新增权限或猜测基础设施，停止并说明阻塞原因。
8. 使用 [references/report-schema.md](references/report-schema.md) 输出“已验证、部分验证、失败或阻塞”的报告。未实际执行的命令不得声称通过。

## 约束

- 优先验证可观察的输入、输出、渲染界面、持久化状态、公开事件和已记录的接口契约。
- 避免断言私有方法、内部状态、ref、偶然调用顺序、DOM 层级、自动生成的 CSS 类或依赖调用；只有当依赖交互本身就是公开契约时才可断言。
- 只模拟无法控制的系统边界，例如网络、时间、随机数、浏览器 API 和第三方系统。对项目自有代码优先使用真实实现或行为可信的轻量替身。
- 不得为了提高覆盖率而测试纯转发、第三方库行为或静态配置。
- 只把覆盖率作为发现测试盲区的线索，不得把它单独作为正确性证明。
- 未经用户明确同意，不得引入测试框架、依赖、服务、夹具环境或具有破坏性的测试准备步骤。
- 无法可靠自动化时，运行项目支持的静态检查或构建，并生成准确的人工验证步骤；结论必须标记为“部分验证”或“阻塞”。

## 框架选择

根据仓库证据选择框架，不得根据文件类型或模型记忆推断。可能的方案包括 Playwright、Cypress、Vitest、Jest、pytest、JUnit、Go test、Rust test 或项目自定义测试器。若项目存在多套方案，根据行为匹配度和同类测试惯例选择；若置信度仍然不足，展示证据并停止编写推测性测试。

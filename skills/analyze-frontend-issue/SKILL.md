# 前端问题分析

先依据现有信息和代码完成分析，再提出修改或排查方案。不要只根据问题标题推测原因。分析结果应让后续执行者可以直接修改或继续排查，避免重新定位一遍。

## 分析流程

### 1. 查看完整问题

- 查看所有已有信息，包括问题描述、验收条件、评论、备注、截图、录屏、日志、Console 或 Network 报错、关联文档、复现步骤、运行环境、影响用户、预期结果和实际结果。
- 实际查看图片和录屏，不要只读附件说明。根据可见的页面、文字和操作入口定位对应路由、组件和代码。
- 对于 Bug，复现或还原操作路径，找到最早出现差异的位置。
- 对于新增任务，明确用户目标、操作入口、预期结果、限制条件和影响范围。
- 使用页面文字、字段名、接口名、报错内容、组件名等信息搜索代码库。
- 明确指出缺失或相互矛盾的信息，不要把推测当作确定结论。

### 2. 追踪数据流向

- 从页面展示或用户操作开始，依次追踪组件、props、本地或全局状态、Hook、表单、Store、接口封装、请求处理和响应转换。
- 找出相关 API 的 HTTP 方法、地址、请求参数、Request Payload、响应字段和调用位置。必要时检查缓存、轮询、分页、防抖、权限和 Feature Flag。
- 有运行环境时，查看浏览器 Network，获取经过请求封装、默认参数、序列化、代理和拦截器处理后实际发出的请求。不要把前端函数传入的几个参数当成完整请求。
- 需要后端协助时，提供浏览器中实际看到的 HTTP 方法、完整请求 URL、全部 Query 参数、完整 Request Payload 或 Form Data、相关 Headers、运行环境、响应状态、Response、Request ID 或 Trace ID。字段名、层级、值和数据类型必须保持原样。
- 内部授权排查时，默认保留 `session`、`sign`、员工号、酒店 ID、时间戳、应用标识、语言、版本、method 和嵌套参数等实际值，不要自动脱敏或替换。
- 只有用户明确要求脱敏，或者内容需要发到授权排查范围之外时，才删除或替换请求值，并说明删除了哪些内容以及该请求是否还能直接复现。
- 无法取得浏览器实际请求时，不要根据源码拼接或伪造完整请求。说明缺少哪一条 Network 记录以及需要补充什么。
- 说明接口字段在展示前是否经过转换、过滤、排序、合并、格式化、默认值、缓存或丢弃。
- 可以查看后端代码时，继续定位路由、Controller、Service、类型、数据库字段或所属模块。没有后端代码时，提供后端能够搜索的完整接口、字段和请求信息。
- 同时追踪查询和提交操作，说明问题或新增逻辑可能进入数据链路的位置。

### 3. 梳理逻辑、类似实现和 Git 历史

- 先完整说明当前位置的业务逻辑，包括进入条件、判断分支、字段来源、默认值、异常处理和最终结果，不要只截取疑似有问题的一行代码。
- 在整个系统中搜索相同或相近的接口、字段、组件、Hook、操作方式、权限判断、校验规则和业务规则。
- 只选择最接近当前问题的实现，不要罗列无关的文本匹配结果。
- 比较请求内容、状态处理、数据转换、加载状态、空状态、错误状态、权限、校验和刷新行为。
- 说明当前逻辑与类似逻辑有何不同，以及差异是业务需要、场景不同、历史遗留、重复实现还是可能的缺陷。
- 已有逻辑符合当前需求时，优先提出复用或保持一致；不适合直接复用时说明原因。
- 使用 Git 记录追踪当前逻辑、关键字段和相关文件的演变。结合 `git log --follow` 查看文件历史，使用 `git blame` 定位相关行的提交，再用 `git show` 阅读每次提交的完整 diff；字段或逻辑被新增、删除或改名时，使用 `git log -S` 或 `git log -G` 继续查找。
- 只保留与当前问题有关的关键修改。每次修改都记录提交哈希、时间、作者、改动内容、修改原因和对当前逻辑的影响；例如三次由不同同事完成的修改，要分别说明每个人改了什么、为什么改，以及后一次修改如何叠加或改变前一次行为。
- 修改原因必须来自提交说明、代码 diff、关联任务或仓库中的其他证据。记录中没有说明原因时，明确写“Git 记录未说明修改原因”，不要根据作者或代码结果编造原因。
- 如果仓库是浅克隆、缺少相关分支、文件历史中断或无法访问关联任务，明确说明 Git 历史的缺口以及需要补充的仓库或记录。

### 4. 给出结论或排查建议

- 有足够证据时，说明根因并给出可执行的修改方案，明确文件、组件、函数、接口和字段。
- 结论必须结合当前逻辑、类似实现、数据流向和 Git 修改历史，说明现状是如何形成的，以及本次修改是否会恢复、覆盖或违背既有业务意图。
- 分析结果应让后续执行者能够直接修改和验证，不需要重新查找页面、接口或类似实现。
- 如果需要与其他系统的数据进行对比，而现有信息无法判断哪一方有问题，不要强行给出根因或要求修改代码，改为给出具体排查建议。
- 需要后端协助时，提供完整浏览器请求和响应、当前系统的值、外部系统的值、两者差异，以及需要后端确认的具体问题。
- 说明需要前端修改、后端修改、双方调整接口约定，还是仅需进一步排查。
- 用户只要求分析时不要直接改代码；用户要求分析并修复时，完成定位后直接修改和验证。

## 固定输出格式

必须严格按照以下四个一级章节输出，顺序不能改变，不要增加单独的前言或总结。

## 问题

说明问题或任务内容、预期结果、实际结果、操作入口、影响范围、已查看的信息和仍然缺失的信息。无法确认的内容要明确标记为待确认。

## 数据流向

说明从页面操作或展示入口，到组件、状态、API、数据转换，再回到页面的完整链路。列出相关文件、函数、HTTP 方法、接口地址、请求和响应字段。需要后端排查时，提供浏览器 Network 中的完整实际请求和响应，不要只提供前端调用函数中的部分参数；除非用户要求或超出授权范围，否则保留请求实际值。

## 类似逻辑

先梳理当前位置的完整业务逻辑，再列出最接近的已有实现及代码位置，说明相同点、不同点，以及应该复用、保持一致还是保留差异。随后列出与当前问题有关的 Git 修改历史，包括提交哈希、时间、作者、改动内容、修改原因和对当前逻辑的影响。没有找到类似实现或完整历史时，说明搜索范围、关键词和缺失原因。

## 解决办法

有明确原因时，给出可以直接执行的修改清单和验证方式。无法判断原因时，给出排查建议，明确由谁检查什么、需要使用哪一份完整请求和响应、需要对比哪些值，以及不同检查结果分别对应的下一步操作。

## 输出前检查

- 已查看现有的问题描述、图片、备注、评论和诊断信息。
- 已找到数据来源和接口，或者明确说明缺少什么。
- 需要后端协助时，提供的是浏览器中的完整请求和响应，而不是前端函数的部分参数。
- 内部授权排查所需的请求值默认保持原样。
- 涉及跨系统数据差异但证据不足时，给出排查建议，不编造根因或修改方案。
- 已梳理当前位置的完整逻辑，并搜索、对比系统中的类似逻辑。
- 已通过 Git 记录查明相关逻辑和字段的关键修改人、修改内容及可证实的修改原因；无法查明的部分已明确说明。
- 文件、函数、接口和字段信息可以被直接定位。
- 四个固定章节各出现一次，并且顺序正确。
